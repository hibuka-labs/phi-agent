# 超时与恢复语义

当一次工具调用被中断——超时、崩溃、或运行被取消——远端动作可能已经执行成功。
本页解释 phi-agent 执行内核如何处理这种不确定性：超时的调用返回什么、恢复后的
会话知道什么、以及为什么恢复时绝不重放已中断的批次。

## 问题背景

工具调用不是纯函数。`send_email`、`refund_payment`、`create_record` 会改变外部
世界，而"调用没有结束"不等于"动作没有发生"：

- 调用可能**在远端已提交之后才超时**；
- 进程可能**在"已开始"和"已结束"之间崩溃**；
- 父 agent 可能**在子 agent 还在工作时停止等待**。

以上任何一种情况下的盲目重试都会产生重复：两封邮件、两笔退款、两条记录。下面的
设计遵循一条不变量：

> **副作用是一次性的。恢复绝不重新执行任何动作。**

## 设计方案

### 超时是普通结果，不是错误状态

每次工具调用都在执行预算内运行。超时后，调用返回一个普通结果，内容是文本
`[Tool Timeout]`——模型像读其他工具输出一样读它，再决定下一步。结构上不存在
独立的"已超时"或"未知"状态；超时就是结果文本的一部分。

执行预算的三个性质：

- **活跃时间，而非墙钟时间。** 工具暂停等待人工（如确认弹窗）的时间会按量延长
  截止时间。用户阅读对话框永远不会造成虚假超时。
- **优先级**：单次调用的 `timeout_ms` 参数（支持该参数的工具）→ 工具自身的
  覆盖值 → 全局配置 → 框架默认（10 分钟）。预算为 `0` 表示不设限——工具自带
  保险丝，或调用是 fire-and-forget。
- **本地取消是尽力而为。** 超时会丢弃进行中的 future，但已经交给外部世界的
  工作无法召回。`[Tool Timeout]` 的含义是*结果未知*，而不是*什么都没发生*。

### 错误交还模型——内核从不自行重试

失败调用的错误会作为工具结果反馈给 LLM，推理循环继续——由模型选择重试、换策略
还是停止。同一工具连续失败多次后，模型会获得一轮携带完整错误历史的宽限回合，
之后运行才会终止。调用路径中不存在任何自动重放，也没有隐式去重层：每一次重试
都是模型（或用户）可见的、有意的行为。

### 检查点标记批次边界

回合运行期间，内核在动作边界写入检查点：

```
CheckpointStep::BeforeActions { actions }        // 每个调用的 id、工具名、参数
CheckpointStep::AfterActions { actions, observation }  // 附带记录的结果
```

检查点以"模型在该回合请求的整批工具调用"为粒度，记录*即将运行什么*（或*运行了
什么、返回了什么*）。

### 恢复是重放，不是重跑

恢复会话时，历史从检查点和记录的观测重建：

```
已完成的批次  ──► 原样重放记录的观测
                  （既有的证据，绝不改写）

悬空的批次    ──► 为每个调用合成一个命运：
  （崩溃窗口）     "已中断/未执行"
                  该批次不会被重新执行
```

悬空批次就是崩溃窗口：进程在 `BeforeActions` 落盘之后、`AfterActions` 落盘之前
死亡。内核无法知道该批次中哪些调用已经到达外部世界，因此如实记录中断，而不会
猜测成功——并且绝不重新执行该批次，因为重跑可能恰好复制那些可能已经发生的副作用。
恢复后模型看到的是一份完整、通过 provider 校验的历史（assistant 工具调用消息 +
每个调用一条结果），以这些合成命运收尾，让下一回合从诚实的起点出发。

具体命运文案取决于恢复入口：检查点重放路径记录 `已中断/未执行`；窗口快照
（`messages.jsonl`）恢复路径则用 `interrupted` 修补悬空调用。两者含义相同——
调用被中断、外部效果未知——都不是"确认没发生"。

### 多 Agent：等待超时不是失败

父 agent 带截止时间等待子 agent 时，截止时间到期的结局是 `Timeout`——一个一等的
非错误结局，含义是*等待结束*，而不是*子 agent 失败*。子 agent 继续运行，结果稍后
进入邮箱，再次等待即可取到。任务在子 agent 内部串行执行，单任务执行超时是可选的
（默认关闭）。

不变量的镜像同样适用：同一个任务发两次就会执行两次。任务没有幂等键，邮箱也没有
去重——如果父侧把 `Timeout` 当失败并重发，子 agent 无法区分重试和新请求。（同一
谨慎原则也驱动着 MCP 客户端的重试策略：`tools/call` 不幂等，因此最多重试一次。）

## 恢复后的会话知道什么

| 问题 | 恢复之后 |
|---|---|
| 被中断的批次原本要执行哪些调用？ | 知道——检查点里有调用 id、工具名、参数 |
| 悬空批次中的调用是否已生效？ | **未知**——记录为中断命运（`已中断/未执行` 或 `interrupted`，依恢复入口而定），不做任何方向的假设 |
| 已完成的批次返回了什么？ | 原样记录的观测 |
| 可安全重试的 provider 幂等键？ | 不提供——该契约属于工具/provider |

## 取舍

- **超时是文本，不是结构化状态。** 简单、与 provider 无关、任何渲染工具输出的 UI
  都能看到——但程序无法在不解析文本的情况下区分超时和普通结果。
- **批次粒度的恢复。** 若三个调用在途、只有第一个提交，恢复后的历史仍会把三个
  折叠进同一个"已中断"命运。逐调用的真相在事件日志（可观测性）里，而不在恢复
  状态里。
- **不内置幂等层。** 内核保持中立：它无法知道哪些工具可以安全重放。去重键（如果
  需要）属于 provider 契约。

## 对安全重试的意义

把 `[Tool Timeout]` 和中断命运（`已中断/未执行`、`interrupted`）当作**未知结局**：

1. **重发之前先核实。** 回读外部状态（邮件发出去了吗？记录存在吗？），而不是
   假设失败。
2. **优先使用带幂等键的工具。** 如果 provider 支持幂等键，用同一个键重发是安全的；
   内核不替你管理这件事。
3. **等待超时不要重发任务。** 再等一次——子 agent 可能已经完成了。
